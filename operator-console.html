Case study · B2B dashboard

PocketPower
Operator Console

A web dashboard for the cafés that host PocketPower stations. It answers one question first: is everything working, and if not, what do I do?

RoleUX/UI designer, solo
TimelineOctober 2026
ToolsFigma, HTML/CSS/JS
TypeConcept project

The problem

PocketPower is a power bank rental app concept for Berlin. A rental app only works if the stations work, and the stations are hosted by partner cafés whose staff are busy with customers. They do not want to study a dashboard. They want to glance at it between orders.

The task I set myself: design the partner side of the product, starting from the situation that matters most, a station that stops working while customers are trying to rent from it.

Honest scope. This is a concept. I did not interview operators, and every number in the screens is sample data. The design rests on assumptions about what a café owner needs (listed below) that I would test before building anything.

Assumptions I designed around

  • Glanceable first. Staff open the console for seconds, not minutes, so the page opens on status, not on reports.
  • Problems should find the user. A broken station is shown as a banner at the top and in a short "Needs attention" list, instead of being hidden in a table.
  • Few people, little training. Actions use plain words ("Mark as serviced") and a short checklist, not technical terms.
  • Revenue matters, but second. One 7-day chart is enough on the overview.

Process

1. Pick the key task

"Find the offline station and mark it as serviced." Everything on the overview exists to get to that task in two clicks: banner → station → checklist → done.

2. Three screens

  • Overview. Four KPIs (stations online, power banks available, rentals and revenue today), an alert banner for the offline station, a 7-day revenue chart and a "Needs attention" list.
  • Stations. A searchable table with filter chips and counts. Sorted so stations that need attention come first. Includes an empty state for searches with no results.
  • Station detail. The reason for the problem in plain words, a 3-step checklist, the last known state of every slot and an activity log.

3. Build on the design system

I built the screens in Figma using the variables, text styles and radii from my PocketPower Design System, so colors and type match the app. The dashboard has denser content than the app, which is a good test of whether the system holds up outside the mobile screens.

4. Check contrast on the new screens

I calculated contrast for every text pair. One failed: the red text in the "Offline" status badge, red #dc2626 on light red #fee2e2, measured 3.95:1, below the 4.5:1 WCAG AA requires for 12 px text. I added a darker red, #b91c1c (5.30:1), as a new token and used it for text in red badges. It should be added to the design system.

5. Make it clickable

I built the three screens as an HTML prototype to test the main task. The "Mark as serviced" button stays disabled until all three checks are ticked and says how many remain. After it is pressed, the station goes online, the banner disappears, the alert counter clears and the KPI changes from 11 / 12 to 12 / 12.

Design decisions

  • Status is never color only. Every status has a text label (Offline, Low stock, Check slot, Online) as well as a color.
  • One primary button per screen. The orange button is the next best action: "View station", then "Mark as serviced".
  • Disabled with a reason. The disabled button explains what is missing instead of leaving the user guessing.
  • Filters show counts. "Offline 1" tells the user something is wrong before they click it.

What I would test next

  • Interview 3 café staff about how they notice a problem today and what they do next. Replace my assumptions with their words.
  • Give 5 people the task "find the broken station and mark it as serviced" and measure time and errors.
  • Build the mobile version, since staff will often check it on a phone behind the counter.
  • Add the new red token to the design system and re-check the dark theme.

What I learned

A dashboard is easiest to get wrong by showing everything. Starting from one task made it clear what to remove from the overview. Checking contrast on a new set of screens also found a failure the app screens never had, so a design system needs testing on content it was not built for.
