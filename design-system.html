PocketPower
Design System

I turned a set of hand-made app screens into a system of tokens, components and rules, and fixed the accessibility problems the audit uncovered.

RoleUX/UI designer, solo
TimelineOctober 2026
ToolsFigma, HTML/CSS
TypeConcept project

The problem

PocketPower is a power bank rental app concept for Berlin. After designing the core flows, I noticed the screens looked coherent but had been built by hand: no variables, no shared components. Before adding more screens I wanted to know how consistent the design really was.

I compared four screens (Scan QR, Scan QR with code input, Map with bottom sheet, Return success) and found:

  • Contrast failures. White text on the brand orange measured 2.73:1, on the amber end of the gradient 1.65:1, and on teal 2.23:1. WCAG AA requires 4.5:1 for normal text and 3:1 for large text.
  • Inconsistent components. The primary button was 60 px tall on one screen and 68 px on another. Secondary buttons were 44 px and 64 px.
  • Duplicate values. Two different orange gradients, radii of 14 and 16 px, two sheet shadow strengths.
  • Missing states. Buttons and the code input existed only in their default state.

I expected a few small inconsistencies. What surprised me was that the brand orange itself, the color I had picked to make buttons feel friendly, failed the contrast requirement with white text.

Process

1. Audit

I extracted colors, type, spacing, radii and shadows from the screens and compared them side by side. I pulled the actual values out of the Figma screens (colors, type sizes, radii, shadows, button heights) into one list, grouped near-duplicates, and marked everything that existed in more than one version.

2. Contrast check

I calculated the WCAG contrast ratio of every text and background pair using the relative-luminance formula, then tested alternatives from the existing palette first.

3. Decisions

  • Text on brand orange: dark brown #3c1600, a color already used on the Continue button. 5.88:1 instead of white at 2.73:1.
  • Orange as text on light surfaces: a darker orange #b4530a, 5.02:1.
  • Text on teal: ink #101828, 7.96:1.
  • Sizes and shapes: three button heights (60 / 48 / 44 px) and four radii (16 / 24 / 32 / pill).

I used dark text on orange instead of darkening the orange, because the bright orange is the brand. A darker orange is used only where orange is text, so the buttons keep their color. Brown text came from the existing palette, so no new color was introduced for buttons. Merging sizes and radii kept the scale small enough to remember.

4. Build

I built the foundations as Figma variables (primitive colors, a semantic Color collection with Light and Dark modes, spacing, radius), text and shadow styles, and components with states: default, hover, pressed and disabled for buttons, plus focus and error for the input. The reference page also shows a loading state. The same tokens are exported as CSS and JSON, and documented on a reference page with usage rules.

What I learned

Brand color and legibility pull in different directions, and the fix was to separate the two: orange stays as a fill, a darker orange is used for text. Naming tokens by role (text/brand, text/on-brand) instead of by color made these decisions easier to see. Next time I would set up the tokens before designing the second screen, not after the fifth.

Next steps

  • Audit the remaining PocketPower screens (this audit covered four).
  • Test the new button colors with 3-5 people outdoors in bright light.
  • Build the remaining components (cards, bottom sheet) in the Figma library.
